L'architecture technique illustrée dans le diagramme présente un système de recommandation en temps réel organisé en couches distinctes et interconnectées. Au sommet se trouve l'Interface Utilisateur composée de l'application cliente qui interagit avec le système. Cette application communique directement avec la couche de messagerie, implémentée via RabbitMQ et gérée par le RabbitMQManager qui assure le cycle de vie des connexions et des canaux. Le broker de messages expose plusieurs files d'attente essentielles, notamment USER_EVENTS, PROCESSED_EVENTS, INTERNAL_REQUESTS, RECOMMENDATIONS, ainsi que diverses files pour les mises à jour (USER_INTERACTIONS, EVENT_UPDATES, PARTICIPATION_UPDATES, FRIENDSHIP_UPDATES).

Au cœur du système se trouve la Pipeline de Traitement qui contient cinq composants clés. Le StreamingConsumer capture les événements utilisateurs bruts depuis la file USER_EVENTS et les transmet au Transformer. Ce dernier convertit ces événements en données exploitables, les stocke via le Repository et publie les événements traités dans la file PROCESSED_EVENTS. Le Recommender analyse ces données transformées pour générer des recommandations personnalisées en s'appuyant sur l'algorithme de recommandation, puis publie les résultats dans la file RECOMMENDATIONS. Le ConsumerManager maintient une communication bidirectionnelle avec les files de référence pour gérer les données contextuelles. Le DataLoader a deux responsabilités principales : le chargement initial des données depuis les repositories au démarrage du système et la mise à jour des consumers en fonction des modifications d'entités reçues via RabbitMQ.

La couche de données comprend plusieurs repositories spécialisés (UserRepository, EventRepository, ParticipationRepository, FriendsRepository, UserInteractionRepository) qui héritent d'un Repository générique, tous connectés à une base de données PostgreSQL. Ces repositories fournissent une interface structurée pour accéder et persister les différentes entités du système.

Les modèles de données centraux incluent User, Event, UserEvent, ProcessedEvent, Recommendation, Participation, Friendship et UserInteraction, qui définissent la structure des données manipulées par le système. L'algorithme de recommandation utilise une approche pondérée : 60% basé sur le comportement actuel de l'utilisateur, 30% sur son contexte social, et 10% sur son historique d'interactions.

Le flux principal de données (représenté par des lignes épaisses vertes dans le diagramme) montre comment les interactions utilisateur traversent le système : depuis l'application cliente vers RabbitMQ, puis vers le StreamingConsumer, le Transformer, les repositories, et enfin vers le Recommender qui génère des recommandations renvoyées à l'utilisateur via RabbitMQ. Des flux secondaires existent entre le DataLoader et les repositories pour le chargement initial des données, ainsi qu'entre les différentes files d'attente et le ConsumerManager pour la gestion des données de référence. Cette architecture modulaire permet un traitement efficace des données en temps réel tout en maintenant un découplage entre les différents composants du système.
